# RabbitMQ headers binding editor audit

This is cycle 1 of the two additional audits requested after the completed PR61/PR62 batch and verified release v1.5.20. The baseline is current `main` at `5e4e615d9bcab4e3b84905b182e2ac8d106b0d25`, the PR62 squash merge. This bounded read-through covered queue-management dialogs/commands, draft validation, message export, rule editing and routing-provider plumbing. Confirmed fixes cover the RabbitMQ headers binding editor and provider persistence boundary; this is not a claim that all reviewed paths are defect-free.

Three correctness problems were reproduced before changing product code:

- A presence condition represented as null in the rule model became the string `"null"` after editing. The initial tests assumed JSON null was the management API representation; live CI later disproved that assumption, as recorded below. Both an unchanged save and changing MATCH reproduced the editor loss. RabbitMQ's [headers-exchange implementation](https://raw.githubusercontent.com/rabbitmq/rabbitmq-server/v4.1.0/deps/rabbit/src/rabbit_exchange_type_headers.erl) confirms that a void argument checks header presence. The editor now treats unquoted `null` as presence and quoted `'null'` as literal text. The shared value parser for other services is unchanged.
- Repeating a header name silently overwrote its earlier value, including names with surrounding whitespace. The dialog now rejects duplicates with an actionable error and stays open. Distinct case-sensitive names remain valid.
- A header-text line named `x-match` overwrote the MATCH dropdown, including an invalid numeric mode that would later be rejected by the broker. The reserved name is now rejected and the operator is directed to the selector.

Test-only commit `a9b55c2edf76d8888af1941f41eaeeafbec33532` preserves seven failing unit cases and two passing controls. The first UI invocation exposed a missing namespace import in the fixture; its compile log is retained. Test-only commit `bcf45786a44903496d4efb076e080ad35cbb4d9b` preserves the corrected fixture, re-proven red on unchanged product code: three failing real-modal-window tests. They exercise TextBox binding and the actual confirm-button event, verify that invalid input keeps the dialog open with a visible error, and inspect the rule returned from saving a presence condition. No assertion was suppressed.

The initial editor-only head `99eed115c31fcdccf467ef05364abc99053b3e36` passed nine new unit cases, 15 focused unit cases, five focused UI cases, and full Windows validation of 1,123 unit / 77 UI tests. This did not establish live binding persistence: the tests stopped at the editor's returned rule. Locked restores and Release solution/Lab builds succeeded with zero warnings/errors; 65 integration cases were explicitly skipped because broker emulators are not configured locally. Independent review correctly found the missing HTTP boundary coverage; the follow-up below supersedes the initial persistence claim.

## Provider-boundary review follow-up

RabbitMQ 4.1's HTTP creation path rejects JSON null: [binding handler](https://github.com/rabbitmq/rabbitmq-server/blob/v4.1.0/deps/rabbitmq_management/src/rabbit_mgmt_wm_bindings.erl) calls `props_to_method`, [management utilities](https://github.com/rabbitmq/rabbitmq-server/blob/v4.1.0/deps/rabbitmq_management/src/rabbit_mgmt_util.erl) convert arguments through [management formatting](https://github.com/rabbitmq/rabbitmq-server/blob/v4.1.0/deps/rabbitmq_management_agent/src/rabbit_mgmt_format.erl), and [rabbit_misc](https://github.com/rabbitmq/rabbitmq-server/blob/v4.1.0/deps/rabbit_common/src/rabbit_misc.erl) throws `null_not_allowed`. Native AMQP void semantics do not imply that HTTP JSON accepts null.

Before the provider fix, `RabbitBindingPersistenceTests` called the real editor and `SaveSubscriptionRuleAsync`; it captured HTTP POST bodies containing `"trace":null`. Eight cases failed, while a quoted-null HTTP control passed. Test-only commit `55e3fc1` preserves the red tests; `34aefe7` completes live-fixture imports. The fake HTTP handler models the source-confirmed rejection and is **not** presented as a live broker response. Compiler diagnostics and corrected behavioral red TRX are preserved. No local emulator environment is configured, Docker/erl commands are absent, and localhost ports 5672/5673/15672/15673 are closed. Docker and security configuration were not changed.

The first provider fix, head `1b8e4ea`, used the existing AMQP connection because [RabbitMQ.Client 7.2.2](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/v7.2.2/projects/RabbitMQ.Client/Impl/WireFormatting.Write.cs) writes null as field type `V`. Its local unit tests passed, but live CI and further review exposed management-response type loss and recovery bookkeeping. That implementation is superseded by the correction below. Queue/exchange destination identity and create-before-delete ordering remain required.

At `1b8e4ea`, nine provider-boundary regressions and 24 combined focused cases passed locally. `RabbitMqUiTests.PresenceBindings_ModalEditorSavesReloadsAndDelivers` adds two broker fixtures, one per destination kind, selected by existing emulator CI. They drive the real modal controls and actual provider. Missing local broker configuration is an explicit skip, never live proof. No workflow/security change is needed.

Windows checks at `1b8e4ea` passed 1,132 unit and 77 UI tests, with one live theory and 65 integrations skipped. These local results did not establish live correctness. Original logs, TRX and source copies remain in `post-v1.5.20-cycle1-20261003/evidence/provider-review`.

## Typed management response and recovery correction

Exact-head CI `37147930537` failed both new broker fixtures during binding identity confirmation. Diagnostic test-only head `91bd249bf820a4319dbb26aa39a5aa506de7f90b`, CI `37148663947`, captured the actual raw management response: `"trace":"undefined"` for an AMQP void argument, for both queue and exchange destinations. This is not JSON null. The diagnostic log is preserved in `evidence/provider-number-review/diagnostic-ci-response.txt`. Literal text `"undefined"` must never be inferred to mean presence.

Binding reads now request the supported `application/bert` response. RabbitMQ's [responder and reply implementation](https://github.com/rabbitmq/rabbitmq-server/blob/v4.1.0/deps/rabbitmq_management/src/rabbit_mgmt_util.erl) sends `term_to_binary(Facts)` for that media type. The bounded data-only [Erlang external term format](https://www.erlang.org/doc/apps/erts/erl_ext_dist.html) reader preserves the distinction between atom `undefined` and binary text `"undefined"`, and between integers and floating values. It accepts the binding resource's maps/proplists, proper lists, binary text, atoms and numbers; checks lengths against remaining input and limits nesting to 64; rejects trailing bytes, duplicate fields, improper lists and unsupported terms including Erlang function/export terms. It does not execute Erlang code. A proxy that substitutes JSON for BERT produces a clear error before replacement.

General [`JsonElement.DeepEquals`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonelement.deepequals?view=net-10.0) treats equivalent numeric representations as equal, and default .NET serialization turns whole-valued double 250.0 into JSON 250. Five provider regressions failed before correction: long-to-double and double-to-long edits, post-bind identity selection with a numeric decoy, and HTTP floating projection. Two unchanged controls and the AMQP creation control passed. The corrected comparator keeps integer/floating categories separate, compares integer magnitudes exactly, compares finite floating values within their category, and respects string/null/bool types, object field names and array order. Floating serialization preserves a decimal or exponent marker for HTTP creation and BERT projection. Unsupported arrays/tables and integers beyond Int64 retain their model types; three further red cases proved the old coercion to text/double, and the editor now rejects these unsupported types rather than changing their meaning.

Presence mutations now create a short-lived AMQP connection with automatic/topology recovery disabled **only for that mutation connection**. Host, credentials, virtual host and TLS settings are shared with normal connection setup. The main connection retains its existing recovery behavior. This prevents native binding records from surviving HTTP replacement/deletion and reappearing on recovery. See the client's [binding recording](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/v7.2.2/projects/RabbitMQ.Client/Impl/AutorecoveringChannel.cs) and [recovery](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/v7.2.2/projects/RabbitMQ.Client/Impl/AutorecoveringConnection.Recovery.cs). An unchanged save keeps the exact properties key. Replacement waits for bind-ok and a uniquely confirmed typed binding identity before deleting the old key; creation or lookup failure retains the old route.

The live fixtures now also verify literal `"undefined"`, integer/double delivery differences in both directions, unchanged floating identity, and replacement/deletion followed by actual broker-forced recovery of the isolated workspace connection. Both queue and exchange fixtures share destination names to check metadata. Raw JSON and BERT response bytes are logged for failures. Final Windows local validation with SDK 10.0.401: locked solution/Lab restores pass, Release solution/Lab builds pass with zero warnings/errors, 1,177 unit tests and 77 UI tests pass. There is one explicit live theory skip (two broker cases) and 65 integration skips because local emulators are absent. Exact-head live emulator CI and full CI remain required before acceptance. All follow-up evidence remains under `evidence/provider-number-review`; earlier evidence is preserved.

## Signed zero and live recovery fixture follow-up

At published head `14ddbb49696c38e974579afce8ff5893c0b4e82a`, CI `37150287639` passed all three OS build/test jobs and all 65 integration cases. Both new live UI fixtures passed creation, editing, typed BERT reads and delivery checks, then failed because the management API had not yet listed the main connection at the immediate recovery lookup. The fixture now waits up to 20 seconds for the exact isolated virtual host and client-provided connection name, rejects ambiguous matches, and retains actual broker-forced recovery assertions. This is condition-based discovery, not a fixed startup delay.

[OTP 27 term comparisons](https://erlang.org/documentation/doc-15.0/doc/system/data_types.html#comparisons) distinguish positive and negative floating zero with `=:=`. Test-only commit `3f8b18a88db3db5ebd6d40f88523100fab717d04` reproduced eight failures and 30 passing controls on unchanged product code: both signed-zero edit directions and numeric decoys, typed identity comparison, and RabbitMQ routing prediction. Finite doubles now compare their IEEE-754 bits in both persistence identity and routing prediction. The BERT and JSON projections preserve the zero sign. The live fixture records RabbitMQ/Erlang versions, requires OTP 27+ for these signed-zero expectations, and checks both directions, unchanged negative-zero identity and actual message delivery. RabbitMQ 4.1 can also run OTP 26, whose historical zero semantics differ; these signed-zero assertions target OTP 27+ explicitly.

Final local Windows validation: 80 focused cases, 1,188 unit tests and 77 UI tests pass; locked solution/Lab restores and Release builds pass with zero warnings/errors. The live theory and 65 integrations remain explicitly skipped locally because emulators are absent. Evidence, red/green TRX and full check logs are retained in `evidence/provider-zero-review`. Exact published-head emulator and full CI remain required before acceptance.

After bind-ok and typed confirmation, a colliding new properties key uses native unbind with the captured original routing key and arguments on the same nonrecovering mutation channel. Missing/ambiguous originals are rejected before mutation. The live test asserts the actual shared hash, singleton typed reload and correct signed-zero delivery.
