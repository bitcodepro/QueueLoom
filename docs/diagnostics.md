# Local diagnostics

Choose **Settings → Export diagnostics**, or **Export diagnostics** beside an operation error or an updater failure. Review the `report.txt` and `diagnostics.json` tabs, then choose a new local ZIP filename. Cancel or close the preview to stop. Dismissing the save picker writes nothing. Existing files are never replaced, including after a save-picker overwrite confirmation. No report is uploaded, sent, or attached to GitHub.

The two files contain the same troubleshooting fields. The report captures an immutable view of the current application session: application assembly version, operating system/version/architectures, known operation kinds, broker type, recorded stages and UTC timestamps, known error categories/codes, and bounded application stack method metadata. Broker addresses and entity references become report-local placeholders. Local paths and all SDK/test/external stack frames are omitted. Placeholder numbers have no meaning across separate reports.

Updater events record checksum verification/mismatch at the actual comparison, installation completion, restart handoff, startup acknowledgement, and verified restoration when these happen in the reporting process. The detached update helper is a separate process; its history is not imported. Previous-session receipts and helper logs are not read. Missing facts stay unknown. A completed UI command may contain a cancelled confirmation or handled partial failure, so command completion alone does not confirm delivery. A successful direct composer send records provider acknowledgement; this does not assert consumer receipt. Only an explicit `DeliveryRejectedException` records a rejected operation.

The journal keeps at most 64 typed events in memory, plus safe context for the most recent 64 operation starts so event eviction does not prevent recording their later results. Updater byte progress updates the UI; only phase transitions enter diagnostics. Profile operations use the profile captured at invocation, without unrelated selected entities; workspace operations use connected context. An unknown endpoint is omitted rather than inferred from presentation text or credentials. Each error event includes at most four exceptions, traversed to nested causes, and three application stack methods per exception. Older events and excess details can be omitted. If necessary, older events are removed from the captured report until the combined UTF-8 files fit 256 KiB; counts identify retention/size omissions. This is a bounded troubleshooting summary, not a complete audit or an operation recovery source.

The exporter never reads logs, Activity prose, settings/configuration files, environment variables, credential vaults, snapshots, backups or command lines. It never collects message bodies or headers, connection strings, arbitrary exception messages, exception `Data`, custom exception type names or raw stacks. The collector maps known constants/enums; unknown/free-text inputs are omitted or replaced with a fixed category. It does not rely on regex redaction of unrestricted text. Operation-specific result details that are not explicitly instrumented remain unknown.

Review before sharing publicly: version, OS version, timing, broker type, error codes and application methods still reveal technical context. This feature minimizes collection; it does not promise secrecy for unrestricted free text in other application displays or files. The ZIP contains only the frozen preview, with fixed entry names and timestamps.

Saving first completes and closes a unique temporary ZIP in the selected directory. Windows publishes it with a native no-replace move; Linux and macOS publish it with POSIX `link()`, which atomically creates a new destination entry and refuses an existing entry, including a dangling symbolic link. Independent exporters or an external creator racing the same filename cannot overwrite one another. On Unix, the chosen local filesystem must support hard links; unsupported filesystems fail without a copying or replacing fallback. Publication does not use a process-only lock or create lock files.

Cancellation is checked while staging and immediately before publication. A cancellation arriving after that final check may leave a successful, complete ZIP; publication is not retracted. Failure or cancellation before publication leaves the destination untouched. Cleanup removes the operation's unique staging path and never deletes the destination, even if another actor has subsequently replaced it. If staging cleanup fails after publication, saving reports an error while the complete destination ZIP and temporary link can remain. Process termination can also leave staging files. This is not an all-or-nothing transaction or a crash-durability guarantee, and cannot prevent another actor from modifying or deleting a ZIP after publication.
