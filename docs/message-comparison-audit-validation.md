# Message comparison audit: incomplete previews and hidden property differences

This is cycle 2, the final one of the two requested audits after PR #60. The baseline is current `main` at `dbfce648512b65048adfd9f614facf6825ea2746`, the squash merge of PR #61. This bounded audit read comparison, consumer metrics, schema decoding, retention, reason grouping and dead-letter backup metadata/cache paths. Confirmed changes are confined to message comparison; this is not a claim that every repository path is defect-free.

The comparison dialog could claim that two messages were identical when:

- Their first 4,000 displayed body lines matched but their unexamined tails differed. Both UTF-8 text and binary previews reproduce this. `AreEqual` now requires a complete body comparison, and an identical truncated prefix is explicitly described as incomplete. The existing preview limit remains in place.
- A provider had already discarded body bytes before comparison. Even a single retained line can represent only a prefix of the original message. Either message's `IsBodyTruncated` now makes the comparison incomplete, with a retained-bytes warning separate from the 4,000-line warning.
- Only `ReplyToSessionId`, `TransactionPartitionKey`, `ScheduledEnqueueTime`, `AmqpType` or `AmqpAppId` differed. These editable broker fields were absent from the comparison. All five are now listed; scheduled enqueue timestamps preserve fractional seconds.
- An application property changed type while retaining the same textual value, such as String `42` versus Int32 `42`. Values now include their type.
- An application property named `Message ID` overwrote the broker property's comparison row. Application rows now have an `Application: ` prefix, so broker and application properties remain distinct.
- Enqueue times differed within the same second. `Enqueued` now uses round-trip formatting instead of dropping fractional seconds.
- Kafka's editable text projection hid differences in raw keys/headers or tombstones. Comparison now also shows the retained Kafka key and ordered raw headers as base64 values, and the tombstone flag.

Test-only commit `2745d63c6e821c49649db68fcee37b18fb03e7e5` preserves nine failing unit cases with one passing control and three failing real-window UI cases before the follow-up product fix. A deterministic test uses the actual Azure mapper: equal-size single-line bodies share their first 1 MiB but differ in discarded tails; their retained bytes and properties match. Other cases cover retained text/JSON/binary previews, left-only/right-only/both-source truncation with equal original sizes and matching normalized JSON, combined source/line limits, complete small binary bodies, and enqueue millisecond differences. All 23 comparison unit cases and six dialog UI cases now pass. Short provider previews explicitly disclose omitted bytes without claiming that 4,000 lines were compared.

The follow-up read-through traced all provider constructors: Azure retains at most 1 MiB and supplies the original size; SQS, Pub/Sub, Kafka and RabbitMQ pass their received bodies directly; JSON backup loading checks the saved body size. Comparison uses `BrowsedMessage.Body`, not the separate character-limited UI/MCP views or `BodyDecoder.Decode` output. Strict UTF-8 decoding preserves valid text; malformed UTF-8 takes the binary hex path. The 64 KiB hex limit produces more than 4,000 lines and is already caught by the comparison line cap. JSON whitespace normalization is existing intended behavior. Application values include both the stored type and invariant text, without shortening/rounding; conversion uses round-trip floats/dates and base64 binary values. Prefixing all application keys separates their namespace from broker keys. The follow-up confirmed enqueue precision loss and the Kafka text-projection gap below. This remains a bounded review rather than a claim about every provider semantic.

The requested binary/string representation check reproduced five more false-equality cases through the actual Kafka mapper on product head `157c77264cdd1e55f275018e97fb8c0fdf8581d5`. These are already retained losslessly in `KafkaEnvelope`, so comparison now includes that key, ordered header list (with null values preserved) and tombstone flag without changing provider mapping.
